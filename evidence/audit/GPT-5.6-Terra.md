# Stash Scraper Builder — Critical Review

**Scope:** `skills/stash-scraper-builder/references/`  
**Review basis:** repository recheck on 2026-08-30  
**Assessment type:** material gaps, risks, and operational optimization  
**Ordering:** highest materiality and risk first

## Executive assessment

The reference set is materially stronger than a basic note collection. It includes focused guidance for schema checks, XPath and JSON patterns, CDP and script runtime modes, post-processing, date/title/performer normalization, failure diagnosis, and an evaluation pack. Recent changes also show active regression-oriented maintenance, including fragment handling, CDP click corrections, nil-pointer troubleshooting, and a six-scenario expected-versus-actual test matrix.

The main unresolved risks are not YAML authoring capability. They are: (1) source authority and version drift; (2) missing explicit controls for API keys, login sessions, cookies, and other secrets; and (3) documented validation that is not yet demonstrably enforced as an executable repository gate.

## Part 1: Material Gaps and Risk

| Serial | Domain | Observation | Recommendations |
|---:|---|---|---|
| 1 | **Authority, provenance, and version drift — High** | Several references identify DeepWiki pages as canonical references, including `schema-checklist.md`, `xpath-patterns.md`, `post-processing.md`, `json-patterns.md`, `date-formats.md`, and `best-practices.md`. This improves traceability. However, the local materials do not visibly pin an upstream CommunityScrapers commit, Stash release, schema revision, or retrieval/review date. Live documentation links can change without a corresponding repository change. | Add `UPSTREAM_SOURCES.md` or `sources.yml`. For each local reference, record the official Stash documentation URL, CommunityScrapers source path, immutable upstream commit SHA, compatible Stash version or range, retrieval date, reviewer, and next review date. Treat CommunityScrapers schema and validator implementation as normative for implementation-sensitive conflicts; use DeepWiki as explanatory context. |
| 2 | **Secrets, login sessions, and API authentication — High** | No easily discoverable dedicated reference was found for `ApiKey`, credentials, secrets, cookie/session handling, browser-profile lifecycle, log redaction, or token rotation. This does not prove all authentication guidance is absent, but it means the required controls are not explicit or easy to locate. | Add `auth-and-secrets.md` before expanding authenticated or API-based scraper support. State non-negotiable rules: never commit live API keys, bearer tokens, cookies, passwords, or browser profiles; use ignored local configuration or supported environment injection; redact sensitive request context from logs; provide empty `.example` placeholders only; document expiry, revocation, and 401/403 recovery; add pre-commit and CI secret scanning. |
| 3 | **Stash GraphQL/API integration — High** | The reference corpus has no dedicated, discoverable Stash GraphQL/API guide. Script actions and post-processing can lead builders to call the Stash API, but the repository does not visibly define authentication, query safety, pagination, error handling, mutation constraints, or idempotency. | Add `stash-graphql-api.md`. Cover endpoint configuration, API-key injection without hardcoding, introspection/schema discovery, read-versus-write boundaries, pagination, error response handling, retry limits, idempotency, and safe examples. Explicitly distinguish external metadata scraping from modifications to a user's Stash library. |
| 4 | **Validation is documented but not proven executable — High** | `schema-checklist.md` cites validation-system and validator-usage guidance. The localized validator guide instructs users to run the official validator, reload Stash, test real URLs, inspect debug logs, and compare key fields. Recent commits added an evaluation matrix covering new, old, missing, multi-value, non-ASCII, and network scenarios. These are strong process controls, but a repository-native automated validator/test runner or CI gate is not established by this review. | Convert the checklist and evaluation pack into a required release gate: YAML parse; pinned upstream schema validation; CommunityScrapers validator; URL routing assertions; fixture-based expected-versus-actual tests; limited lawful live smoke tests; secret scan; and stored validator/test artifacts. Do not mark a scraper as validated merely because a checklist was read. |
| 5 | **Login and CDP operational safety — Medium-High** | `cdp-workflow.md` exists, and recent maintenance corrected CDP click behavior to use XPath with optional sleep/wait behavior. CDP steps were also placed in regression expectations. The operational model is improving, but a discoverable policy for login, challenge completion, persistent browser state, session expiry, and cleanup is not evident. | Keep CDP as an escalation path, not a default. Add a runtime decision and safety policy: use public static XPath/JSON first; use CDP only for client-rendered or interaction-dependent content; use visible/manual login only when authorized; never commit browser profiles or cookies; define timeouts, cleanup, stale-session detection, and a predictable fallback when authentication expires. |
| 6 | **Product-level source selection — Medium** | The corpus is implementation-rich: XPath, JSON, scripts, CDP, post-processing, field cleaning, network scrapers, failures, and schema guidance. It is less visibly organized around the prior decision of whether a scraper is the right tool versus a Stash-box/metadata source, a manual workflow, or no automation. | Add `source-selection.md` with a concise decision table. Example: source-specific metadata → scraper; broad community identity or tag enrichment → Stash-box; static public HTML → XPath; structured public endpoint → JSON; authenticated or multi-step interaction → script/CDP only when justified. Require a short choice rationale in each scraper request or PR. |
| 7 | **Architecture and interface boundaries — Medium** | The components are covered across separate references, but no clearly central end-to-end architecture is evident: entry point → URL routing → action runtime → extraction → post-processing → result → validation → reload/debug cycle. Contributors can therefore make locally plausible changes that conflict with routing precedence or runtime assumptions. | Add `architecture.md` containing one diagram and one worked example. Identify ownership of URL matching, HTTP/CDP/script retrieval, extraction, normalization, validation, error reporting, and Stash reload/debug behavior. |
| 8 | **External-site fragility and source health — Medium** | `scraping-failures.md` was recently expanded with nil-pointer troubleshooting, a `sceneByFragment` example, runtime-safety links, and verification checks. This is a positive signal. Yet no source-health state, last-verified date, ownership, or retirement policy is apparent. | Track each source as active, degraded, blocked, or retired. Store safe test URLs or fixtures, last verified date, known anti-bot constraints, owner, and disable/rollback procedure. Avoid aggressive automated retry behavior that can worsen blocks or conflict with source terms. |
| 9 | **Reference discoverability and cognitive load — Medium-Low** | There are many useful specialized documents, including title and performer handling, date formats, multi-site patterns, validation guides, runtime modes, and failure diagnosis. The risk is not insufficient information; it is that a contributor may not know which material is mandatory versus conditional. | Add a task-to-reference load order in `SKILL.md`: always read the schema checklist, failures guide, and evaluation pack; select exactly one primary runtime path; load specialized patterns only when applicable; run validation before delivery. |
| 10 | **Internationalization and semantic data quality — Low-Medium** | The references contain substantive safeguards: preserve meaningful CJK title brackets and punctuation, retain performer separators such as `・` and `-`, avoid unsupported gender defaults, and use Go reference layouts for `parseDate`. These protect source semantics rather than merely formatting output. | Retain the rules and make them fixture-backed: CJK title, Japanese performer separator, alias-bearing name, ambiguous gender, localized date, invalid/missing date, and multi-performer output. Do not permit cleanup rules that silently discard meaningful source data. |

## Part 2: Operational Optimization

| Serial | Domain | Observation | Recommendations |
|---:|---|---|---|
| 1 | **Gated delivery pipeline — Highest leverage** | The repository already contains the core ingredients: schema material, a checklist, validator-error guidance, failure diagnosis, and an evaluation pack with a six-scenario matrix and expected-versus-actual checks. | Establish the default workflow: **design → generate complete YAML → schema/validator check → fixture evaluation → limited real-URL smoke test → secret scan → review**. Require every stage for new or materially changed scrapers; allow a lighter path only for documentation-only changes. |
| 2 | **Source pinning and scheduled review** | Canonical DeepWiki links now appear in several references, which is better than unattributed guidance. The remaining reproducibility weakness is that the links are mutable. | Pin implementation rules to immutable CommunityScrapers commits. Perform review quarterly or after upstream Stash/CommunityScrapers releases. Check schema changes, validator changes, release notes, and broken assumptions, then record the review date and outcome. |
| 3 | **Runtime-choice decision gate** | Dedicated XPath, JSON, script, and CDP references exist, and recent CDP corrections demonstrate active attention to runtime behavior. A contributor can still choose an overly complex runtime before assessing a simpler option. | Require each CDP/script proposal to answer: "Why are XPath or JSON insufficient?" Use a default escalation sequence: XPath → JSON → script → CDP only when necessary. This reduces browser fragility, latency, maintenance cost, and credential exposure. |
| 4 | **Deterministic fixtures versus live checks** | The evaluation pack covers useful data and network cases, but external sites are volatile. Live checks alone cannot be a deterministic regression signal. | Maintain two test layers: saved deterministic fixtures for selectors, transforms, and post-processing; and limited live smoke tests for availability/routing. Fixture failure should block release. Live failure should trigger evidence-based investigation, not immediate speculative selector rewrites. |
| 5 | **Source-specific observability** | Existing failure guidance requires debug-log inspection, which is a sound baseline. The review does not establish a standardized evidence package for reporting/triaging failures. | Standardize failure reports with scraper/version, input URL, Stash version, runtime mode, HTTP status or CDP state, sanitized request context, failing selector/API field, expected versus actual value, useful fixture/screenshot where appropriate, and last-known-good revision. |
| 6 | **URL routing and precedence protection** | A scraper can satisfy schema validation yet route an input URL to the wrong entry point or be shadowed by another definition. Recent fragment-related checks are a positive step, but routing should be independently asserted. | Add routing tests for each entry point: intended URL → expected scraper/action; near-match URL → must not match; shared-domain URL → expected precedence. Run these tests whenever URL regexes, multi-site maps, or route ordering change. |
| 7 | **Turn quality guidance into assertions** | Best-practice and field-quality work already specifies important behavior: anchors, studio mappings, fallback handling, image upgrades, title transformation order, and performer-name safeguards. Prose alone is easy to overlook. | Mechanize the highest-value rules: title must not be empty when a title source exists; date parsing failure must be visible; valid performer punctuation must survive cleaning; image URLs must be valid; fallback logic must not overwrite stronger values. Keep prose for rationale, assertions for enforcement. |
| 8 | **Reduce duplicated mutable rules** | Specialized references are valuable, but repeated rules across documents tend to diverge over time unless one location is explicitly primary. | Define an owner document for every rule category: schema in `schema-checklist.md`; runtime in `cdp-workflow.md`/`script-actions.md`; transformations in `post-processing.md`; recovery in `scraping-failures.md`. Link to the owner instead of copying mutable rule text. |
| 9 | **Contributor onboarding by task** | The recent workstream/review cycle suggests active refinement. The likely operational bottleneck is consistent navigation and application of the material. | Add three task-based entry paths: "Build a public page scraper," "Build a JSON/API scraper," and "Diagnose a broken scraper." Each should list required reading, prohibited shortcuts, tests, and definition of done. |
| 10 | **zh-TW quick layer with terminology control** | Several documents contain concise zh-TW operational summaries, lowering friction for local contributors. Configuration tokens, error messages, field names, API labels, XPath, regex, and schema keys must remain exact. | Retain English as the normative technical specification and zh-TW as the quick-operational layer. Preserve exact English technical tokens and explain them in zh-TW rather than translating configuration keys or machine-readable values. |

## Decision

Retain the reference set and use it for conventional scraper-building work. Before treating it as an authoritative, reusable, and maintainable specification package, implement the first four priority controls: immutable source/version provenance, explicit secret and authentication policy, dedicated GraphQL/API guidance, and executable validation/release gates.
